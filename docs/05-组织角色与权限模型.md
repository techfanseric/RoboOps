# RoboOps 组织角色与权限模型

整理日期：2026-07-05
系统英文名：RoboOps
系统中文名：机器人商业运营平台

## 1. 背景判断

RoboOps 面对的很多甲方会是机器人公司、具身智能公司、自动化设备公司或新成立的运营主体，他们通常从较小团队开始建立商业运营能力。

这类客户的典型问题是：

- 他们懂机器人、AI、硬件或工程，但不一定懂商业运营。
- 他们可能没有客服、点位运营、区域管理、财务结算、现场维护等完整岗位。
- 他们会把“运营问题”误认为“工程接口问题”，导致需求直接压给工程师。
- 他们不知道异常应该分给谁处理，也不知道什么权限应该给什么人。
- 业务规模从 1 个样板点到几十个点位变化很快，组织结构不能一开始写死。

因此，RoboOps 不应该只是提供后台功能，还应该提供一套“推荐运营组织模型”。系统要能反向指导客户：做这门机器人商业运营业务，至少需要哪些职责，随着规模扩大应该补哪些角色，哪些权限必须隔离，哪些角色可以一人兼任。

一句话判断：

> RoboOps 的角色权限是产品帮助客户建立运营能力的一部分。

## 2. 设计目标

角色与权限模型需要满足 5 个目标。

### 2.1 指导客户搭团队

系统应能告诉客户：

- 当前规模需要哪些最小角色。
- 哪些角色可以兼职，哪些角色不建议合并。
- 业务扩大后应该新增哪些岗位。
- 哪些异常应该由客服、运维、运营、财务或现场人员处理。
- 哪些动作需要审批，哪些动作可以直接执行。

### 2.2 支持不同规模阶段

1 个样板点、10 个试点点位、50 个城市点位、200 个多品牌点位，需要的组织模型不一样。

系统应支持：

- 小规模一人多岗。
- 中等规模职责分离。
- 大规模区域化、班组化、中心化。
- 多品牌、多区域、多供应商、多合作方的权限隔离。

### 2.3 支持可配置角色

角色不能写死为固定岗位，例如“老板、客服、运维、财务”。

更合理的方式是：

- 系统内置推荐角色模板。
- 客户可复制模板并调整权限。
- 角色由权限包、数据范围、审批能力、通知订阅、异常分派规则组成。
- 同一个人可以拥有多个角色。
- 同一个角色可以限定在某个品牌、区域、点位、设备组或场景模板内。

### 2.4 支持安全和审计

机器人商业运营涉及退款、设备控制、停业、配置下发、异常关闭、人工接管等高风险动作。

系统必须支持：

- 最小权限。
- 数据范围隔离。
- 高风险动作二次确认。
- 必要审批。
- 操作留痕。
- 紧急权限和事后审计。

### 2.5 支持业务闭环

权限不只是“菜单能不能看”，还要决定业务流转。

例如：

- 订单异常分派给谁。
- 设备离线通知谁。
- 退款谁能发起，谁能审批。
- 配置谁能编辑，谁能发布。
- 点位停业谁能执行，谁能恢复。
- 报表谁能导出。

## 3. 核心概念区分

### 3.1 岗位、角色、权限不是一回事

| 概念 | 含义 | RoboOps 中的设计方式 |
| --- | --- | --- |
| 岗位 | 客户组织里的真实职位，例如运营经理、现场维护员 | 系统不强行固定，只作为用户资料或组织说明 |
| 系统角色 | 一组责任和权限组合，例如点位运营、异常处理、设备运维 | 可配置、可复制、可限定范围 |
| 权限包 | 某类功能动作集合，例如订单处理包、设备运维包 | 可复用，供角色组合 |
| 数据范围 | 角色能管理哪些品牌、区域、点位、设备 | 与角色授权绑定 |
| 责任归属 | 某类异常、任务、审批默认由谁负责 | 与异常规则、任务规则、通知规则绑定 |

这意味着：

- 一个“运营经理”岗位可以拥有运营管理、报表查看、异常分派三个系统角色。
- 一个“创业公司负责人”早期可以同时拥有业务负责人、运营负责人、配置审批人角色。
- 一个“外部维修商”只能拥有某些点位的设备查看和工单处理权限，不能查看收入和退款。

### 3.2 权限模型不能只有 RBAC

基础可以采用 RBAC，也就是用户通过角色获得权限。但 RoboOps 还需要叠加数据范围、审批规则和动作风险等级。

建议模型：

> 用户 User + 角色 Role + 权限包 Permission Package + 数据范围 Data Scope + 审批策略 Approval Policy + 审计日志 Audit Log

这样才能表达：

- 某用户是客服，但只负责上海区域。
- 某用户能处理异常，但不能审批退款。
- 某用户能编辑商品，但不能发布到点位。
- 某用户能查看设备日志，但不能重启设备。
- 某用户能导出订单，但不能导出财务明细。

## 4. 经营组织的几种模式

RoboOps 应同时支持以下几种经营组织模式。

### 4.1 客户自营

客户自己经营点位、自己承担运营结果。

常见角色：

- 客户老板/业务负责人。
- 运营负责人。
- 客服/售后。
- 现场维护/补给。
- 机器人/设备运维。
- 财务/结算。

适合：

- 机器人公司自己探索商业化。
- 新品牌自建机器人门店/点位。
- 小规模试点和城市复制。

### 4.2 平台代运营

RoboOps 提供方或合作运营公司帮助客户运营。

常见角色：

- 平台运营负责人。
- 客户业务负责人。
- 平台客服。
- 平台设备运维。
- 客户只读/审批角色。

适合：

- 甲方没有运营团队。
- 甲方只想看结果和关键审批。
- 前期用代运营帮客户跑通业务。

### 4.3 联合运营

客户、平台、点位方、设备方共同参与。

常见角色：

- 客户业务负责人。
- 平台运营经理。
- 点位负责人。
- 现场服务商。
- 机器人供应商支持。
- 财务或结算复核。

适合：

- 商场、景区、展厅、机场等点位合作。
- 设备厂商和运营方分离。
- 多方共同承担异常处理。

### 4.4 加盟/区域代理

品牌或机器人业务复制到多个区域，区域方或加盟商负责部分运营。

常见角色：

- 总部品牌管理员。
- 区域运营经理。
- 加盟商管理员。
- 点位运营人员。
- 总部审计/财务。

适合：

- 多城市扩张。
- 多品牌或白标经营。
- 后续规模化商业复制。

## 5. 按规模阶段的团队建议

### 5.1 S0 展示/POC 阶段：1-3 个点位

目标：证明业务能跑通，能卖单，能处理基本异常。

推荐最小团队：

| 职责 | 是否必须 | 可否兼职 | 说明 |
| --- | --- | --- | --- |
| 业务负责人 | 必须 | 可兼运营负责人 | 对业务结果负责，决定是否继续投入 |
| 系统管理员 | 必须 | 可由平台方代管 | 建品牌、点位、人员、权限 |
| 运营负责人 | 必须 | 可由业务负责人兼任 | 每天看订单、点位、异常 |
| 机器人/设备负责人 | 必须 | 可由工程或供应商兼任 | 处理离线、故障、日志、设备恢复 |
| 客服/异常处理 | 必须 | 可由运营兼任 | 处理订单异常、未取货、退款沟通 |
| 现场执行 | 必须 | 可由点位人员或外包兼任 | 补料、清洁、现场恢复 |
| 财务复核 | 建议 | 可兼职 | 看收入、退款、结算记录 |

系统推荐：

- 使用“最小运营团队模板”。
- 允许一人多角色。
- 高风险权限仍要分开，例如退款审批和配置发布尽量不要完全由同一人长期承担。

### 5.2 S1 试点阶段：3-20 个点位

目标：形成可复制的日常运营流程。

推荐团队：

| 职责 | 建议人数 | 说明 |
| --- | --- | --- |
| 业务负责人 | 1 | 看经营结果、预算、点位扩张 |
| 运营经理 | 1 | 负责点位运营、异常闭环、SOP |
| 系统/配置管理员 | 0.5-1 | 配品牌、商品/服务、场景模板、权限 |
| 客服/售后 | 1-2 | 处理订单异常、退款、顾客沟通 |
| 机器人/设备运维 | 1-2 | 处理设备状态、日志、远程恢复 |
| 现场维护/补给 | 1-3 | 根据点位密度配置 |
| 财务/结算 | 0.5 | 退款复核、收入核对、导出报表 |
| 数据/复盘 | 0.5 | 统计异常原因、点位表现 |

系统推荐：

- 运营和设备职责开始分开。
- 客服可处理异常，但退款审批建议由运营经理或财务复核。
- 配置编辑和配置发布建议分开。
- 点位开始绑定负责人。

### 5.3 S2 城市复制阶段：20-50 个点位

目标：从项目试点变成稳定经营。

推荐团队：

| 职责 | 说明 |
| --- | --- |
| 城市/区域运营经理 | 对区域点位 GMV、订单、异常率、在线率负责 |
| 运营调度/值班人员 | 盯工作台、异常、任务、通知 |
| 客服组 | 处理顾客反馈、退款、补偿 |
| 机器人运维组 | 处理远程诊断、设备恢复、版本问题 |
| 现场服务组 | 巡检、补料、清洁、维修、现场应急 |
| 商品/服务配置负责人 | 管理上新、价格、上下架、模板 |
| 财务/结算 | 对账、退款复核、点位分账准备 |
| 数据分析 | 点位效率、异常排行、复购/转化分析 |

系统推荐：

- 引入区域/点位数据范围。
- 引入异常等级和 SLA。
- 引入值班或通知路由。
- 引入审批流：退款、停业、配置发布。
- 引入操作审计和导出权限控制。

### 5.4 S3 规模化阶段：50-200 个点位

目标：标准化、区域化、中心化。

推荐组织：

- 总部业务负责人。
- 总部运营负责人。
- 区域运营经理。
- 点位运营负责人。
- 运营指挥中心/NOC。
- 客服主管与客服组。
- 机器人运维主管与运维组。
- 现场服务主管与区域服务队。
- 商品/服务目录负责人。
- 配置发布负责人。
- 质量/SOP/培训负责人。
- 财务结算负责人。
- 数据分析负责人。
- 安全/审计负责人。

系统推荐：

- 角色模板按总部、区域、点位分层。
- 报表按总部、区域、品牌、场景、点位聚合。
- 异常支持升级路径。
- 配置发布支持范围、版本、回滚、审批。
- 外包服务商只获得对应点位和工单权限。

### 5.5 S4 多品牌/多租户阶段：200 个点位以上

目标：平台化经营。

推荐组织：

- 平台超级管理员。
- 租户管理员。
- 品牌管理员。
- 场景模板管理员。
- 区域/加盟商管理员。
- 合作方管理员。
- API/集成管理员。
- 安全审计员。
- 财务/结算管理员。
- 客户成功/交付经理。

系统推荐：

- 多租户强隔离。
- 白标/品牌级权限。
- 伙伴和供应商权限。
- 更细的数据脱敏和导出审批。
- 更完整的审计、风控、合规记录。

## 6. 推荐角色族

RoboOps 不应只内置几个简单角色，而应建立“角色族”。客户可以从角色族中选择模板。

### 6.1 经营决策角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 业务负责人 | 对机器人商业业务结果负责 | 查看全局经营数据、审批关键动作、查看报表 |
| 品牌负责人 | 对某品牌经营负责 | 管理品牌范围内点位、商品/服务、报表 |
| 项目负责人 | 对某次试点或客户项目负责 | 查看项目点位、跟踪上线进度和异常 |

注意：

- 经营决策角色通常不应直接执行高风险设备命令。
- 他们需要审批权和全局视图，但不一定需要所有编辑权。

### 6.2 运营管理角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 运营负责人 | 负责日常经营和跨角色协同 | 点位管理、订单查看、异常分派、任务跟进、报表查看 |
| 区域运营经理 | 负责某区域点位表现 | 区域点位、区域异常、区域任务、区域报表 |
| 点位负责人 | 负责单点位运行 | 点位状态、点位订单、点位异常、现场任务 |
| 运营调度/值班 | 负责实时监控和派单 | 工作台、异常分派、任务分派、通知处理 |

注意：

- 运营是业务闭环的中心。
- 运营不一定能修改底层设备配置。
- 运营可以停业或申请停业，但是否可直接恢复营业要按客户风险偏好配置。

### 6.3 商品/服务与配置角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 商品/服务管理员 | 管理可售商品、服务、SKU、上下架 | 商品/服务创建、编辑、上下架 |
| 场景模板管理员 | 管理饮品亭、服务站等模板 | 场景字段、状态显示名、异常字典 |
| 配置发布人 | 将配置发布到点位或设备 | 配置发布、版本记录、回滚申请 |
| 配置审批人 | 审批关键配置发布 | 审批发布、查看差异、回滚审批 |

注意：

- 编辑配置和发布配置建议分开。
- 价格、可售范围、履约状态、设备模板属于高影响配置，需要审计。
- MVP 可先做简单审批，后续再做复杂审批流。

### 6.4 订单、客服与售后角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 订单处理员 | 处理订单状态、人工确认 | 订单查看、状态备注、异常关联 |
| 客服/售后 | 处理顾客问题、未取货、退款沟通 | 订单详情、异常处理、退款发起 |
| 退款审批人 | 控制退款风险 | 退款审批、退款记录查看 |
| 投诉处理人 | 处理复杂客诉 | 客诉记录、补偿建议、升级处理 |

注意：

- 客服需要看到订单和异常上下文，但不一定需要看到完整财务报表。
- 退款发起和退款审批最好分离。
- 退款、补偿、关闭异常必须留痕。

### 6.5 机器人/设备运维角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 机器人运维工程师 | 处理机器人运行、日志、远程恢复 | 设备状态、日志、命令记录、远程恢复动作 |
| 设备运维工程师 | 处理制饮设备、柜体、传感器等 | 设备详情、故障处理、维护记录 |
| 远程值班/NOC | 监控在线率和故障 | 设备监控、告警处理、任务分派 |
| 供应商支持 | 协助特定型号设备排障 | 限定设备日志、限定工单处理 |

注意：

- 设备命令要分风险等级。
- 查看日志、重启设备、停止营业、清空本地数据、推送配置不应是同一等级权限。
- 供应商支持只能看与自己相关的设备和工单。

### 6.6 现场服务角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 现场维护员 | 到点位处理问题 | 查看点位任务、维护记录、上传处理结果 |
| 补给/物料人员 | 补料、清洁、耗材检查 | 物料任务、点位状态、补给记录 |
| 巡检人员 | 定期巡检和拍照确认 | 巡检任务、现场照片、检查清单 |
| 点位合作方 | 提供现场协助 | 只看自己点位的任务和基础状态 |

注意：

- 现场角色通常不应查看完整收入和客户信息。
- 现场角色需要移动端友好的任务视图。
- 对于饮品亭，物料/清洁任务是现场角色的关键工作；对于其他服务场景，可以替换为场地检查、耗材更换、机器人回充等任务。

### 6.7 财务、数据与审计角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 财务/结算 | 处理收入、退款、对账 | 收入报表、退款记录、导出、结算数据 |
| 数据分析 | 看经营效率和异常趋势 | 报表查看、数据导出、点位分析 |
| 审计员 | 检查操作合规 | 操作日志、权限变更记录、高风险动作记录 |

注意：

- 财务可看钱，但不一定能改商品、设备、点位配置。
- 数据分析可看报表，但不一定能导出敏感明细。
- 审计员应只读，不参与日常处理。

### 6.8 平台与系统管理角色族

| 角色模板 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 平台超级管理员 | RoboOps 平台方最高权限 | 跨租户管理、系统配置、故障支持 |
| 租户管理员 | 客户组织内最高系统管理员 | 用户、角色、品牌、组织、数据范围 |
| 权限管理员 | 管理账号和授权 | 用户邀请、角色分配、权限审计 |
| 集成管理员 | 管理 API、支付、设备接入 | 接口配置、Webhook、密钥占位 |

注意：

- 平台超级管理员必须和客户数据访问做强审计。
- 租户管理员不应自动拥有所有业务操作权，特别是退款和设备危险命令。
- API 密钥、支付配置、设备接入配置需要单独权限。

## 8. 权限设计框架

### 8.1 权限维度

每个角色应由以下维度组合而成。

| 维度 | 说明 | 示例 |
| --- | --- | --- |
| 模块权限 | 能进入哪些模块 | 点位、设备、订单、异常、报表 |
| 动作权限 | 能执行哪些动作 | 查看、创建、编辑、删除、发布、审批 |
| 数据范围 | 能操作哪些数据 | 某品牌、某区域、某点位、某设备组 |
| 风险等级 | 动作危险程度 | 查看日志、重启设备、停业、退款 |
| 审批要求 | 是否需要他人确认 | 退款审批、配置发布审批 |
| 通知订阅 | 收到哪些提醒 | 设备离线、订单异常、退款待审 |
| 默认责任 | 哪类任务默认分给谁 | 未取货给客服，离线给设备运维 |

### 8.2 动作权限分级

| 等级 | 类型 | 示例 |
| --- | --- | --- |
| L0 只读 | 只查看，不改变业务 | 查看列表、查看详情、看报表 |
| L1 普通编辑 | 对低风险资料编辑 | 编辑点位电话、维护备注 |
| L2 业务影响 | 会影响交易或运营 | 上下架、改价格、关闭异常、发起退款 |
| L3 高风险操作 | 会影响设备或点位营业 | 重启设备、停业、恢复营业、发布配置 |
| L4 敏感管理 | 会影响组织安全 | 分配权限、导出财务、API 密钥、跨租户支持 |

### 8.3 权限包建议

| 权限包 | 包含能力 |
| --- | --- |
| 工作台查看包 | 查看工作台、关键指标、待处理事项 |
| 点位运营包 | 查看/编辑点位、设置营业状态、绑定负责人 |
| 商品服务管理包 | 管理商品/服务、SKU、上下架、适用点位 |
| 配置发布包 | 创建发布、查看版本、回滚申请 |
| 订单处理包 | 查看订单、备注、关联异常、人工确认 |
| 客服售后包 | 处理异常、发起退款、记录沟通 |
| 退款审批包 | 审批退款、查看退款明细 |
| 设备查看包 | 查看设备状态、日志、事件 |
| 设备运维包 | 处理设备异常、执行低风险命令、维护记录 |
| 设备高危命令包 | 重启、停机、清空、远程控制等高风险命令 |
| 现场任务包 | 查看和完成补给、维护、巡检任务 |
| 报表查看包 | 查看经营、点位、异常、设备报表 |
| 报表导出包 | 导出明细数据 |
| 用户权限管理包 | 邀请用户、分配角色、设置数据范围 |
| 审计查看包 | 查看操作日志、权限变更、高风险动作记录 |

角色模板通过组合权限包产生。

### 8.4 数据范围模型

数据范围建议支持以下层级：

- 全平台。
- 租户。
- 品牌。
- 组织/区域。
- 城市。
- 点位。
- 设备组。
- 单台设备。
- 场景模板。
- 商品/服务类型。

典型表达：

- 某客服只能看品牌 A 的上海区域订单。
- 某现场维护员只能看 5 个点位的任务。
- 某供应商只能看自己型号设备的日志。
- 某加盟商只能看自己加盟区域的收入汇总，不能看其他区域。

## 9. 可配置角色的数据结构建议

### 9.1 角色模板

角色模板用于客户创建角色时复用；授权给用户的是角色实例。

建议字段：

- 模板名称。
- 模板说明。
- 适用业务规模：POC、试点、城市复制、规模化。
- 适用经营模式：自营、代运营、联合运营、加盟。
- 推荐岗位说明。
- 默认权限包。
- 默认数据范围类型。
- 默认通知订阅。
- 默认异常责任。
- 默认审批能力。
- 风险提示。

### 9.2 角色实例

客户实际使用的是角色实例。

建议字段：

- 角色名称。
- 所属租户。
- 所属品牌。
- 来源模板。
- 权限包列表。
- 数据范围。
- 是否允许转授权。
- 是否允许导出。
- 是否允许高风险动作。
- 是否需要二次验证。
- 启用状态。

### 9.3 用户授权

一个用户可以有多个角色。

建议字段：

- 用户。
- 角色实例。
- 数据范围。
- 生效时间。
- 失效时间。
- 授权人。
- 授权原因。
- 是否临时权限。

### 9.4 异常分派规则

异常分派要和角色挂钩。

建议字段：

- 异常类型。
- 严重等级。
- 来源：订单、设备、支付、机器人、人工。
- 适用场景模板。
- 适用品牌/点位。
- 默认负责人角色。
- 升级负责人角色。
- SLA。
- 通知渠道。
- 是否允许自动关闭。
- 是否允许转退款。
- 是否允许转现场任务。

### 9.5 审批策略

建议第一版至少预留审批策略。

建议字段：

- 动作类型。
- 触发条件。
- 审批角色。
- 金额阈值。
- 数据范围。
- 是否允许发起人自审。
- 是否必须双人审批。
- 超时处理。

典型策略：

- 退款金额超过阈值需要审批。
- 配置发布到超过 5 个点位需要审批。
- 点位停业超过 2 小时需要运营负责人确认。
- 设备高危命令需要二次确认和留痕。

## 10. 团队搭建向导

RoboOps 可以把“团队搭建”做成客户 onboarding 的一部分。

### 10.1 向导问题

系统可以询问：

- 当前是自营、代运营、联合运营还是加盟？
- 第一批预计多少个点位？
- 是单品牌还是多品牌？
- 点位是否跨城市？
- 是否有自己的客服？
- 是否有自己的现场维护人员？
- 设备运维由客户、平台还是供应商负责？
- 是否需要处理支付和退款？
- 营业时间是否需要夜间值守？
- 是否有外部点位方或合作方需要登录？

### 10.2 自动生成结果

根据回答，系统生成：

- 推荐组织结构。
- 推荐角色模板。
- 建议账号清单。
- 默认权限包。
- 默认数据范围。
- 默认异常分派规则。
- 默认审批策略。
- 默认通知订阅。
- 上线前检查清单。

### 10.3 示例：客户没有运营团队

如果客户选择“没有现成运营团队”，系统应推荐最小运营组织：

- 业务负责人：客户老板或项目负责人。
- 运营负责人：可以先由平台或客户项目经理兼任。
- 客服/异常处理：可以先由平台代运营或客户指定人员承担。
- 机器人/设备负责人：客户工程团队或设备供应商承担。
- 现场执行：点位方、外包服务商或客户地推人员承担。
- 财务复核：客户财务兼职。
- 系统管理员：平台交付人员先协助，后移交客户。

并提示：

- 工程师不应长期承担客服和运营决策。
- 退款、停业、配置发布需要有人负责审批。
- 每个点位必须有现场联系人。
- 每类异常必须有默认负责人。

## 12. 异常类型与默认责任

| 异常类型 | 默认负责人 | 升级对象 | 说明 |
| --- | --- | --- | --- |
| 支付失败 | 客服/售后 | 运营负责人 | 先判断用户支付状态和订单状态 |
| 已支付但未下发 | 运营调度 | 机器人/设备运维 | 需要确认订单系统和设备通信 |
| 机器人接单失败 | 机器人/设备运维 | 运营负责人 | 判断设备、网络、机器人状态 |
| 执行超时 | 运营调度 | 机器人/设备运维 | 需要看是否继续等待、取消或退款 |
| 制作/服务失败 | 机器人/设备运维 | 客服/售后 | 技术原因确认后客服处理用户 |
| 顾客未取走 | 客服/售后 | 点位负责人 | 需要顾客沟通或现场确认 |
| 取货判断不确定 | 运营调度 | 现场维护员 | 可能需要人工确认 |
| 物料不足 | 现场维护员 | 运营负责人 | 可转补给任务 |
| 设备离线 | 机器人/设备运维 | 现场维护员 | 远程恢复失败后转现场 |
| 点位环境问题 | 点位负责人 | 运营负责人 | 包括断电、场地封闭、人流管控 |
| 退款争议 | 客服/售后 | 退款审批人 | 必须留存处理记录 |
| 配置错误 | 商品/配置管理员 | 配置审批人 | 需要发布修正并记录影响范围 |
| 安全风险 | 运营负责人 | 业务负责人 | 可触发紧急停业和高优先级通知 |

## 13. MVP 需要落地的系统能力

### 13.1 必做

- 用户管理。
- 组织/区域管理。
- 角色模板。
- 角色实例。
- 权限包。
- 数据范围授权。
- 用户多角色绑定。
- 基础审批策略。
- 异常默认负责人配置。
- 通知订阅配置。
- 操作日志。
- 高风险动作二次确认。

### 13.2 可以简化

- 先不做复杂排班，只做默认负责人和通知人。
- 先不做完整审批流，只做单级审批和记录。
- 先不做复杂数据脱敏，只做导出权限和财务权限隔离。
- 先不做 HR 组织管理，只做运营所需组织/区域/点位层级。

### 13.3 暂不做

- 薪资、绩效、考勤。
- 完整客服工单系统。
- 完整 ITSM/ITIL 流程。
- 完整值班排班系统。
- 复杂多级审批流。
- 外部 IAM/SSO 深度集成。
- 细粒度字段级权限。

## 14. MVP 权限矩阵草案

符号说明：

- V：查看。
- M：管理/编辑。
- A：审批。
- P：发布。
- E：导出。

## 15. 系统界面建议

角色权限相关界面不应只做一个传统权限树。建议包括：

### 15.1 团队搭建向导

- 选择经营模式。
- 选择点位规模。
- 选择是否自有客服、运维、现场团队。
- 自动推荐角色。
- 自动生成待邀请人员清单。
- 自动生成异常分派规则。

### 15.2 角色模板库

- 最小运营团队模板。
- 试点运营团队模板。
- 城市复制团队模板。
- 多品牌总部模板。
- 平台代运营模板。
- 联合运营模板。
- 展会/Demo 模板。

### 15.3 角色详情页

- 角色说明。
- 适用岗位。
- 权限包。
- 数据范围。
- 可审批动作。
- 可执行高风险动作。
- 默认负责异常。
- 通知订阅。
- 当前用户列表。
- 风险提示。

### 15.4 用户授权页

- 用户基础信息。
- 组织归属。
- 已绑定角色。
- 每个角色的数据范围。
- 临时权限。
- 最近操作记录。

### 15.5 权限风险检查

系统可以提醒：

- 某用户同时拥有退款发起和退款审批。
- 某用户拥有全局导出权限但不是财务或审计。
- 某外部供应商拥有跨品牌数据权限。
- 某角色拥有设备高危命令但没有二次验证。
- 某点位没有负责人。
- 某异常类型没有默认负责人。

## 16. 对客户的团队搭建建议

RoboOps 可以内置一段面向客户的建议：

### 16.1 不要把所有事情交给工程师

机器人公司常见误区是让工程师直接处理订单、退款、客诉、点位运营。短期能救火，长期会导致：

- 工程团队被运营琐事拖住。
- 客户体验没有责任人。
- 异常没有业务判断。
- 数据无法复盘。

### 16.2 最小运营团队至少覆盖 6 类职责

即使一人多岗，也要有人负责：

- 业务结果。
- 日常运营。
- 客服/异常。
- 机器人/设备。
- 现场执行。
- 财务复核。

### 16.3 每个异常都必须有默认负责人

如果异常没有负责人，后台只会变成告警堆积器。

必须明确：

- 谁第一时间收到。
- 谁判断原因。
- 谁联系顾客。
- 谁决定退款。
- 谁到现场处理。
- 谁关闭异常。

### 16.4 权限要随规模逐步拆开

POC 阶段可以一人多岗，但到 20 个点位后，应逐步拆分：

- 运营与设备运维分离。
- 客服与退款审批分离。
- 配置编辑与发布审批分离。
- 现场服务与财务数据分离。
- 外部供应商与客户经营数据分离。

## 17. 数据模型补充

在 `04-RoboOps系统规划与MVP框架.md` 的数据模型基础上，建议新增或细化以下实体。

- `team_templates`：团队模板，例如最小运营团队、城市复制团队。

## 18. 需要验证的事实与配置选择

以下问题用于落地角色模板和权限配置，不是让没有经验的甲方从零设计组织。建议由 RoboOps 先给默认团队方案，再让客户确认谁承担、谁审批、哪些职责由平台代管。

- 第一批客户是希望自营，还是希望平台代运营？
- 客户是否已有客服团队？
- 客户是否已有现场服务能力？
- 设备运维由客户、平台还是机器人供应商负责？
- 是否需要夜间或 7x24 小时响应？
- 支付和退款在 MVP 中由谁承担？
- 是否需要外部点位方登录系统？
- 是否会有加盟商或区域代理？
- 高风险设备命令是否允许客户执行？
- 平台支持人员访问客户数据时需要什么审批和审计？
