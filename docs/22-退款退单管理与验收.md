# 退款 / 退单管理：实现说明与验收

实施日期：2026-09-20。发布版本：v0.2.2（用户验收通过）。范围：RoboOps 前端演示，不包含小程序开发及真实支付接入。

## 页面与入口

- 入口：订单请求 → 退款 / 退单管理；路由 `/orders/refunds`。
- 订单概览、点位订单与执行增加导航；订单详情及异常处理中的退款动作跳转统一页面，携带原订单号。
- 三个视图：订单处理、退款记录、批次记录。支持订单/父单/设备搜索、点位、履约、退款、来源、时间与退单状态筛选。
- 默认按后台子单选择；切换小程序整单选择时，关联勾选当前权限范围内同父单的全部子单，并提示可能包含筛选外订单。跨权限的订单不展开、不操作。整单选择不等于无条件整单全退。
- 翻页和筛选变化清除旧选择。当前页选择明确显示订单数、关联订单数和预计金额。
- 确认时显示可处理、需审核、跳过及逐单原因；金额可调整为部分退款。提交仍执行完整业务校验。

## 业务规则

| 履约 / 结果 | 默认行为 | 可演示变化 |
| --- | --- | --- |
| 失败 | 人工发起、免审核 | 自动退款：对新失败回执触发，不追溯历史订单 |
| 待制作 | 直接退款，先取消履约 | 直接、审核或禁止退款 |
| 制茶中 | 审核后退款，先取消履约 | 直接、审核或禁止退款 |
| 已完成 / 已取餐 | 审核后售后退款，不退单 | 直接、审核或禁止退款 |
| 已取消 | 可按剩余实付退款 | 已退完不可重复退 |
| 异常待确认 | 不等同于失败，暂不可退 | 演示回执可确认失败并转为免审 |
| 退单失败 | 暂停依赖退单的退款，继续保留金额 | 详情重试退单，成功后继续原退款 |
| 支付结果未知 | 保留金额，禁止新申请 | 查询原退款更新结果，不生成新退款单 |
| 明确退款失败 | 释放该次申请占用 | 新建退款申请重试，保留原失败记录 |
| 历史订单缺支付关联 | 不可支付退款，明确展示待补齐 | 后续由接入层补齐，不从商品原价推算 |
| 手工未支付订单 | 可按履约状态退单，不能退款 | 不生成虚构支付记录 |

失败订单免审核不受其他状态禁退策略影响，但仍检查支付关联、余额和已有处理中申请。若待审核 / 待退单期间收到明确失败事件，原申请转为免审核执行，避免重复申请。

“先退单再退款”策略关闭时，退款独立执行，履约可以继续；界面明确提示这一影响。退款成功不会覆盖履约状态。取消履约成功也不会自动把支付记为已退款。

规则配置要求企业全部订单点位范围，局部账号不能通过修改企业策略影响授权外点位。发起和审核分离，同一账号不能审核自己的申请；审核通过仍要重查当前状态和余额。

## 金额与结果

- 金额统一以人民币分保存，显示时转换为元。
- 子单支付分摊金额与父支付总额分别保存，示例父单三条子单为 18 + 22 + 20 = 60 元。
- 成功退款及待审核、待退单、处理中、结果未知申请占用余额；驳回及明确失败释放占用。
- 同一支付内各子单共同受父支付总额限制，不跨租户合并同号支付。
- 批次 token 防重复提交，批内订单去重；其他批次也不能重复退款处理中订单。
- 模拟回执约 1.8 秒推进一次：设备回执与支付回执分两步，不将“已提交”当成“已到账”。离开页面会暂停模拟推进，再进入继续处理。
- 退款批次追踪关联退款单；设备退单批次保留该次尝试的结果，不被下一次重试覆盖。
- 操作时间线记录申请、审核、设备回执和支付回执；人工动作同时进入原主系统审计。

## 仿真场景与操作步骤

推荐账号：林砚 / `usr-000`；演示密码见 README。可配置策略、发起退款、审核他人申请。

### 推荐快速验收

1. 用 `TD-pt-001` 搜索，全选本页 10 条，点击批量退款，填售后原因。
2. 确认金额 150 元：4 条免审、4 条需审、2 条跳过。
3. 等待模拟回执：2 条成功、1 条失败、1 条结果待确认、4 条待审核、2 条跳过。
4. 去退款记录查询未知结果，重试明确失败的退款；自身发起的审核按钮应禁用。
5. 搜索 `TD-pt-001-014`，审核预置客服申请，检查通过/驳回与记录。
6. 在处理规则中切换失败订单为自动退款，再对未处理的制茶中订单模拟失败回执：免审核自动生成退款。
7. 使用审计员叶青 / `usr-014` 验证只读；用点位负责人许诺 / `usr-007` 检查仅深圳湾范围可见。
8. 恢复时进入“处理规则 → 演示数据管理 → 恢复演示订单 → 确认”。仅恢复当前权限范围的 TD 演示订单，不删除历史请求，不重置规则；把规则改回默认即可重复上述验收。

## 现有模块边界

- 原订单概览的请求自动作为历史订单投影进入本页面；因为旧字段不包含支付明细，不能仅凭 `amount` 伪造可支付退款。
- 原“点位订单与执行”的手工订单和设备退单继续属于旧设备仿真链路。其 `refundState` 仍表示设备退单下发状态，本次在确认文字中明确“不退回支付金额”；新模块使用独立的 `cancelStatus` 与退款单状态。未将两套历史数据强行按金额/名称匹配。
- 异常列表和详情的退款入口已跳转新管理页面；旧审批历史与旧 `RefundCase` 保留在原系统，不自动迁移成渠道退款记录。
- 新增完整仿真订单、退款与批次使用 `roboops-refunds-v1` 本地存储，租户/点位隔离通过现有账号范围过滤。它不是多用户后端，浏览器间无服务端并发保证。
- v0.2.2 经用户验收后通过 `main` 分支发布到 Cloudflare Pages 生产演示站点；未开发小程序或调用真实支付。
