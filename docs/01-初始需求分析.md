# RoboOps - 机器人商业运营平台初始需求分析

版本：v0.1
整理日期：2026-07-05
依据材料：2026-06-27 通话转录

## 1. 项目背景

原来的业务模式更接近“设备能力供应商”：

- 公司与喜茶、茶百道、茶颜悦色等品牌方合作，主要提供机械臂/自动化设备及相关设备管理能力。
- 后台更多是物联网设备管理后台，关注设备是否正常、订单量等基础设备运行信息。
- 配方、门店运营、订单异常、退款、客诉、人员分工等运营能力，过去主要由品牌方自己负责。

现在出现了新的客户类型：人形机器人公司。

- 多家人形机器人公司希望把原有咖啡/奶茶自动化方案，改造成“人形机器人开店/开亭子”的商业模式。
- 这些公司擅长机器人本体或 AI 能力，但并不擅长 C 端商业运营、门店管理、订单管理和异常处理。
- 通话中提到，除了人形机器人本体不是己方提供，其他系统能力、终端小程序、下单链路、设备方案等很多都在己方体系内。
- 已经有约三家公司提出类似需求，深圳也已有若干试点点位。

由此产生的问题是：只提供 API 已经不够了。客户无法仅凭 API 把业务跑起来，也无法把订单、设备、机器人异常、支付、退款、取货、运营人员分工等流程串成稳定的日常运营体系。

因此需要把原来的设备能力升级为一个通用产品：RoboOps - 机器人商业运营平台。

## 2. 产品定位

RoboOps 是机器人商业场景的运营底座，饮品亭是第一批样板场景之一。

它要解决的是：当机器人或自动化设备进入真实商业场景后，如何让点位能够被管理、订单能够被履约、异常能够被处理、人员能够协同、数据能够被追踪、模式能够被复制。

更具体地说，它应该是一个连接以下对象的平台：

- 点位：门店、亭子、柜体、工作站、展点、服务站。
- 设备：机械臂、人形机器人、咖啡机、制茶设备、传感器、柜门、屏幕、取餐口等。
- 商品/服务：咖啡、奶茶、零售商品、机器人服务、未来其他自动化服务。
- 流程：下单、支付、制作/执行、完成、取货/交付、异常、退款、结算。
- 人员：客户方运营人员、总部管理员、区域负责人、点位运维、客服、财务、工程支持。
- 系统：小程序、支付系统、设备 API、机器人状态 API、订单系统、消息通知、数据看板。

## 3. 关键判断

### 3.1 这是可复制的标准产品

通话里反复提到，不同客户提出不同需求，工程师被定制需求消耗严重。因此 RoboOps 的核心价值之一，是把这些需求抽象成可配置产品，让客户差异沉淀为可复用模板。

当前第一批场景可能是咖啡/奶茶亭，但产品架构不能写死“饮品”。

### 3.2 这是面向运营闭环的系统

已有 API 并不是难点，真正的问题是：

- API 没有被串成业务流程。
- 客户不知道什么状态该由谁处理。
- 订单、设备、机器人判断异常、退款、未取货等事件没有形成闭环。
- 客户无法从一堆接口里理解运营动作。

因此后台不能只是展示 API 字段，而要提供“可执行的运营工作台”。

### 3.3 人形机器人带来了传统设备运营没有的新异常

传统咖啡/奶茶运营里，人类店员会自然处理很多模糊情况。但机器人场景会新增一类“机器人判断/交互/执行异常”，例如：

- 机器人是否正确理解订单或指令。
- 机器人执行动作是否成功。
- 机器人与设备之间的协同是否中断。
- 机器人判断顾客是否取走商品时是否误判。
- 机器人、人、设备之间的通信链路是否异常。

这类异常需要被产品化，作为工程日志之外的运营对象存在。

### 3.4 第一阶段目标是能跑起来、能卖单

通话中明确提到，两个月窗口期内不追求一步到位，先做一个版本，让试点能够运营起来，至少能卖单、能处理基本订单与异常。

因此 MVP 应聚焦日常运营闭环，复杂中台能力放到后续阶段。

## 4. 目标用户与角色

### 4.1 客户方老板/项目负责人

关注：

- 点位是否正常营业。
- 今日订单和收入如何。
- 哪些点位异常多。
- 投放是否值得继续扩大。
- 是否能快速复制到更多点位。

需要：

- 总览看板。
- 点位/设备健康状态。
- 订单、收入、退款、异常数据。
- 多点位对比。

### 4.2 运营负责人/区域经理

关注：

- 多个点位的营业情况。
- 异常是否被及时处理。
- 商品/服务流程是否配置正确。
- 人员是否按职责响应。

需要：

- 点位列表与状态筛选。
- 异常工单/任务分派。
- 商品/流程配置。
- 订单与退款处理。
- 运营报表。

### 4.3 点位运维人员

关注：

- 哪个点位需要补料、维修、重启或现场处理。
- 机器人/设备是否离线或异常。
- 是否有顾客未取、订单卡住、制作失败等问题。

需要：

- 移动端友好的任务列表。
- 点位设备状态。
- 异常详情与处理 SOP。
- 处理结果回填。

### 4.4 客服/售后人员

关注：

- 用户支付成功但未收到商品/服务。
- 订单异常、退款、投诉。
- 未取货、重复支付、制作失败等情况。

需要：

- 订单查询。
- 订单状态流转记录。
- 异常原因。
- 退款/补偿入口。
- 与用户沟通所需的信息。

### 4.5 财务/结算人员

关注：

- 收入、退款、手续费、结算。
- 点位、客户、商品维度的收支情况。

需要：

- 收支报表。
- 退款记录。
- 结算数据导出。
- 对账依据。

### 4.6 平台内部产品/工程/交付人员

关注：

- 不同客户如何快速上线。
- API、设备、点位、小程序之间如何配置。
- 客户需求如何沉淀为标准能力。

需要：

- 客户/租户管理。
- 接口配置与日志。
- 场景模板。
- 状态字典与异常字典。
- 权限与数据隔离。

## 5. 已谈及的初步需求

以下需求均来自通话内容的直接提取或合理归纳。

### 5.1 点位与设备管理

- 管理客户投放的机器人点位，例如亭子、门店、自动咖啡站、自动奶茶站。
- 查看点位数量、分类、位置、当前营业状态。
- 查看每个点位绑定的机器人、机械臂、制饮设备、取货设备、屏幕等。
- 查看设备是否正常、是否离线、是否需要人工介入。
- 支持深圳试点等小规模点位先跑起来，后续支持规模化复制。

### 5.2 订单状态管理

通话中明确提到当前缺少后台看到这些状态：

- 订单已生成。
- 支付中/支付成功。
- 制作中/执行中。
- 制作完成/服务完成。
- 待取货。
- 顾客已取走。
- 顾客未取走。
- 订单异常。
- 退单/退款。

这些状态需要形成统一订单生命周期，API 字段只是其中的事实来源。

### 5.3 支付与退款

- 支持查看支付状态。
- 支持订单退单/退款处理。
- 支持异常订单触发退款或人工审核。
- 支持收入、退款、收支统计。
- 后续可能需要与微信支付/支付宝/小程序支付链路对账。

### 5.4 机器人与设备异常管理

这是 RoboOps 与普通门店后台最不同的部分。

需要沉淀异常类型，例如：

- 机器人判断异常。
- 机器人执行异常。
- 机器人与设备通信异常。
- 设备离线。
- 制作失败。
- 取货判断异常。
- 顾客未取货。
- 订单卡在某个状态。
- API 调用失败。
- 需要现场人工介入。

每类异常都应该对应：

- 异常来源。
- 严重程度。
- 影响订单/点位/设备范围。
- 推荐处理人。
- 推荐处理动作。
- 是否自动恢复。
- 是否需要通知客户/运维/客服。

### 5.5 商品/服务流程配置

通话中特别提到咖啡和奶茶业务流不一样，不能每个客户都定制。

因此需要把“商品/服务流程”做成可配置能力：

- 不同品类可以有不同履约流程。
- 同一类商品可以配置不同步骤。
- 支持咖啡、奶茶等饮品场景作为第一批模板。
- 后续可扩展到零售、取货、机器人服务、实验室自动化工作站等其他商业场景。

第一阶段不一定要做复杂流程引擎，但至少要有“场景模板 + 状态配置 + 异常配置”的产品思路。

### 5.6 角色与权限

通话中明确提到需要搞清楚“什么样的人、什么场景、什么权限”。

初步需要：

- 平台超级管理员。
- 客户管理员。
- 客户运营负责人。
- 区域/点位负责人。
- 运维人员。
- 客服人员。
- 财务人员。
- 只读观察者。

后续 `05-组织角色与权限模型.md` 已将这里的初步角色扩展为“角色族、角色模板、权限包、数据范围、审批策略、异常默认负责人”的完整模型。这里保留为初始分析，不应理解为固定岗位清单。

权限至少覆盖：

- 能看哪些客户/点位/订单。
- 能否处理异常。
- 能否退款。
- 能否修改商品/流程配置。
- 能否管理设备。
- 能否导出数据。
- 能否发布配置。
- 能否执行高风险设备命令。
- 能否审批退款、停业、配置发布等高影响动作。
- 所有高风险动作是否留痕。

### 5.7 小程序与消费者端链路

通话中提到，小程序下单也挂在己方后台，终端消费者使用的东西也是己方在做。

因此 RoboOps 需要和小程序链路打通：

- 商品/服务配置是否同步到小程序。
- 小程序订单如何进入后台。
- 支付状态如何同步。
- 顾客取货/未取货状态如何回传。
- 异常时消费者端显示什么状态。

RoboOps 不一定直接负责消费者端 UI，但要成为消费者端订单与运营后台之间的业务中枢。

### 5.8 数据看板

客户首先需要“看得见运营状态”。

初步看板应包含：

- 今日订单数。
- 今日销售额。
- 支付成功订单数。
- 异常订单数。
- 退款金额/退款率。
- 点位在线率。
- 设备异常数。
- 未取货订单数。
- 各点位销售排行。
- 各点位异常排行。

### 5.9 API 与系统集成

通话中提到已有一堆 API，但客户无法使用。

RoboOps 需要把 API 能力变成产品能力：

- 统一接入订单、支付、设备、机器人状态。
- 对外隐藏 API 复杂度。
- 对内保留 API 日志、事件追踪、错误排查能力。
- 支持新客户上线时快速配置接口和点位。

### 5.10 竞品与参考

通话中提到需要找类似竞品，也提到竞品后台难以直接看到，只能看消费者端、截图、试用或通过投放合作了解。

当前可参考的方向：

- 机器人咖啡/无人咖啡亭。
- 自动奶茶/自动饮品设备。
- 无人零售/无人货柜。
- 连锁门店运营系统。
- 外卖/新零售订单后台。
- IoT 设备管理后台。
- 工单/运维系统。

但需要注意：不能直接搬茶百道等既有客户系统，也不能复用有版权风险的客户方案。

## 6. 建议的产品模块

### 6.1 总览工作台

用于老板、运营负责人快速了解整体状态。

核心内容：

- 订单、收入、退款、异常、点位在线率。
- 异常优先级提醒。
- 点位排行。
- 需要处理的任务。

### 6.2 点位管理

管理商业投放单元。

核心内容：

- 点位列表。
- 点位详情。
- 点位营业状态。
- 位置、客户、场景类型。
- 绑定设备/机器人。
- 点位运营数据。

### 6.3 设备/机器人管理

管理点位中的自动化设备与机器人。

核心内容：

- 设备在线/离线。
- 设备健康状态。
- 机器人状态。
- 最近异常。
- API/心跳/日志摘要。
- 远程诊断入口。

### 6.4 订单中心

管理从下单到履约完成的订单生命周期。

核心内容：

- 订单列表。
- 订单详情。
- 支付状态。
- 制作/执行状态。
- 取货/交付状态。
- 异常状态。
- 退款状态。
- 状态流转记录。

### 6.5 异常中心

把机器人商业运营中最需要人工介入的部分集中起来。

核心内容：

- 异常列表。
- 异常类型。
- 异常来源。
- 影响订单/点位/设备。
- 处理责任人。
- 处理状态。
- 处理记录。
- 是否触发退款/补偿/工单。

### 6.6 运营任务/工单中心

将异常、补料、维修、巡检、人工确认等动作变成任务。

核心内容：

- 任务列表。
- 任务分派。
- 处理进度。
- 处理结果。
- 超时提醒。
- 操作留痕。

### 6.7 商品/服务配置

支持不同商业场景的履约配置。

核心内容：

- 商品/SKU 管理。
- 售卖状态。
- 价格。
- 制作/履约流程模板。
- 可选项/规格。
- 与小程序展示同步。

### 6.8 场景模板

让平台从饮品走向通用。

第一批模板可以包括：

- 机器人咖啡亭。
- 机器人奶茶亭。
- 自动饮品站。

未来可扩展：

- 机器人零售点位。
- 机器人导购/服务站。
- 自动化取货站。
- 实验室自动化工作站。

### 6.9 财务与结算

支持客户看清楚钱。

核心内容：

- 收入统计。
- 退款统计。
- 点位维度收支。
- 商品维度收支。
- 对账导出。
- 结算状态。

### 6.10 权限与组织

支持多客户、多点位、多角色协作。

核心内容：

- 客户/租户管理。
- 组织架构。
- 角色权限。
- 数据范围。
- 操作日志。

## 7. MVP 建议

### 7.1 MVP 目标

两个月窗口期内，先让试点客户能够运营起来。

标准是：

- 能看见点位与设备状态。
- 能看见订单状态。
- 能处理基础异常。
- 能处理退款/退单。
- 能看基础营收和异常数据。
- 能支持客户运营人员分工。
- 能接入已有 API，把接口能力转成客户可直接运营的系统。

### 7.2 MVP 必做

- 租户/客户边界、品牌、组织、角色的基础框架。
- 场景模板，至少包含“饮品亭”和“通用机器人服务站”两个样板。
- 点位管理，以及点位与机器人/设备绑定。
- 机器人/设备台账、在线状态、运行状态和事件日志。
- 商品/服务目录，支持自定义属性、规格/SKU、上下架和适用点位。
- 订单/服务请求列表与详情。
- 订单/服务请求生命周期状态，底层状态通用，界面显示名按场景配置。
- 异常中心，包含异常类型、分派、处理状态、处理记录和关闭。
- 基础退款/退单记录与退款审批扩展位。
- 简单运营看板，覆盖点位、设备、订单/请求、异常、任务、收入占位。
- 用户、角色、权限包、数据范围和基础审批策略。
- 小程序订单或模拟订单接入。
- 设备/机器人状态或模拟事件接入。
- 配置发布记录。
- 操作日志和高风险动作留痕。

### 7.3 MVP 可简化

- 流程配置先做“场景模板”，不急着做完整流程引擎。
- 财务先做基础统计和导出，不急着做复杂结算。
- 运维工单先做异常处理记录，不急着做完整工单系统。
- 多租户可以先满足客户隔离和权限隔离，不急着做 SaaS 级复杂能力。

### 7.4 暂不建议放入第一版

- 复杂 AI 预测。
- 自动补货算法。
- 高级 BI。
- 大规模流程编排引擎。
- 复杂库存系统。
- 完整 CRM/会员系统。
- 全渠道营销系统。

## 8. 初步状态模型

### 8.1 订单主状态

建议初步抽象为：

1. 已创建
2. 待支付
3. 已支付
4. 待执行
5. 已分配/已下发
6. 执行中
7. 执行完成
8. 待交付/待取货
9. 已交付/已取货
10. 未交付/未取货
11. 异常
12. 已取消
13. 退款中
14. 已退款

### 8.2 异常状态

建议初步抽象为：

1. 新异常
2. 已分派

## 9. 边界与风险

### 9.1 不要被“饮品亭”限制

饮品是第一场景，但产品抽象应围绕：

- 点位
- 设备/机器人
- 商品/服务
- 订单/任务
- 异常
- 运营人员
- 数据

这样后续才能扩展到其他机器人商业场景。

### 9.2 不要直接复刻客户后台

已有大品牌项目可以作为经验来源，但不能直接搬迁界面、流程、文案或私有方案。需要从业务规律重新抽象。

### 9.3 最大难点在运营逻辑

通话中已明确：API 本身不难，难的是把 API 串成客户能理解、能操作、能分工的流程。

### 9.4 客户可能说不清需求

人形机器人公司自身并不一定懂饮品/零售运营，不能完全等客户给需求。需要站在“连锁运营老板”的视角主动设计方案。

### 9.5 需要处理人机协作的不确定性

机器人场景比普通自助设备多了感知、判断、动作执行和人机交互异常。RoboOps 必须把这些异常显性化。

## 11. 一个更准确的项目表述

RoboOps 的目标是把人形机器人饮品亭这一样板场景抽象成可复制的机器人商业运营平台：

> 为机器人进入真实商业场景后的规模化运营，提供一套标准化、可配置、可复制的运营管理平台。

饮品亭是第一个落地点，未来真正有价值的是“机器人商业运营的通用操作系统”。
