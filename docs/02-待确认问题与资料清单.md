# RoboOps 已知判断、自研假设与待确认资料清单

整理日期：2026-07-05
修订说明：本文件根据原始通话重新调整口径。RoboOps 面向的甲方大概率是在全新开展机器人商业运营业务，本身缺少成熟运营经验，因此不能把关键产品问题都设计成“等待甲方回答”。更合理的方式是：由我们基于通话信息、已有项目经验、竞品调研和深入思考先提出标准方案，再让客户选择、验证和配置。

## 1. 核心修正

原先的“待确认问题”里，有不少问题看似应该问甲方，但从通话内容看，甲方其实很难回答。

原因是：

- 甲方多为人形机器人公司或自动化设备公司，不是成熟连锁品牌。
- 这项业务对他们来说是新业务，他们未必有客服、运营、点位、财务、现场维护等完整团队。
- 他们擅长机器人技术，但不一定懂 C 端商业运营、连锁点位经营、退款售后、异常分派和日常 SOP。
- 如果直接问他们“你们需要什么角色、什么流程、什么权限”，他们很可能给不出可落地答案，或者只把零散问题甩给工程师。

因此，RoboOps 的产品规划原则应调整为：

> 不等甲方定义运营系统，而是由 RoboOps 提供一套可配置的推荐运营模型，让甲方按业务规模、经营模式和组织能力选择、裁剪和验证。

## 2. 原始通话中已经给出的答案

以下问题不应再作为开放问题反复问甲方，通话里已经基本给出答案。

### 2.1 甲方是什么类型

已知判断：

- 第一批典型甲方是人形机器人公司。
- 他们希望把咖啡、奶茶等自动化制饮模式迁移到“人形机器人开店/开亭子”的商业场景。
- 他们不是传统饮品品牌，也不是成熟连锁运营方。
- 他们大概率缺少完整商业运营团队。

规划影响：

- 系统必须承担“指导客户建立运营能力”的职责。
- 不能假设客户已经知道订单、退款、异常、客服、现场运维该怎么分工。
- 团队模板、角色模板、异常分派规则、上线检查清单应该成为产品能力。

### 2.2 当前最大问题是什么

已知判断：

- 过去己方主要管设备和 IoT 后台，品牌方负责运营。
- 现在机器人公司没有现成运营系统，只给 API 没有意义。
- 最大难点不是技术接口，而是把接口串成可执行的运营逻辑。

规划影响：

- RoboOps 不能做成 API 字段展示台。
- 必须围绕点位、订单/服务请求、设备/机器人、异常、人员、任务、报表形成闭环。
- 工程日志要转化成运营可理解的异常和任务。

### 2.3 第一版目标是什么

已知判断：

- 有两个月窗口期。
- 第一版不追求一步到位。
- 先让试点能够运营起来，至少能卖单、能看状态、能处理基本异常。
- 规模可能不是很大，通话里提到几十个亭子、深圳已有若干试点。

规划影响：

- MVP 重点是框架和闭环，不是做完整中台。
- 优先级应是：场景模板、点位、订单生命周期、异常中心、角色权限、基础报表。
- 复杂库存、完整财务、完整 OTA、复杂工作流引擎可以后置。

### 2.4 产品边界是否只限饮品

已知判断：

- 咖啡/奶茶是第一批场景，但不应限制在饮品。
- 不同客户会提出不同需求，不能每家定制。
- 需要形成标准化、可配置的运营模式。

规划影响：

- 系统底层应使用“商品/服务”“场景模板”“履约流程”“资源消耗”等通用概念。
- 饮品亭只是一个场景模板，不应写死在核心模型里。
- 品牌、商品、流程、异常、角色、报表口径都应可配置。

### 2.5 谁来定义运营岗位和权限

已知判断：

- 通话中已经明确提出：“什么样的人、什么场景、什么权限”需要我们主动想清楚。
- 对方客户自己很难写出这些东西。
- 应站在“连锁运营老板”的视角看问题。

规划影响：

- 角色与权限不能只等客户提供组织架构。
- RoboOps 应内置团队模板和角色模板。
- 客户可以一人多岗，但系统必须显性化每类职责。

## 3. 问题分类方式

后续所有问题建议分成三类。

### 3.1 A 类：我们已经可以直接判断

这类问题不再问甲方，而是写入产品假设和默认方案。

示例：

- 第一版不能只做饮品，应支持通用场景模板。
- 甲方缺少运营团队，系统要提供团队搭建指导。
- 订单需要完整生命周期。
- 异常需要独立异常中心。
- 角色权限需要支持数据范围、审批和审计。
- 客户差异要通过配置承载，而不是每家定制开发。

### 3.2 B 类：我们应先给方案，再让甲方验证

这类问题不适合空问，而应先提供推荐方案，让客户选择或修正。

示例：

- 客户方有哪些角色？
- 退款该谁发起、谁审批？
- 哪些异常归客服，哪些归设备运维？
- 点位上线流程应该怎么走？
- 商品/服务流程配置到什么粒度？
- 订单状态应该如何命名？

处理方式：

- 我们先给默认角色模板、权限矩阵、异常分派规则。
- 甲方只需要确认“是否有人承担这些职责”“哪些职责暂时由平台代管”“哪些动作他们希望自己审批”。

### 3.3 C 类：仍然必须向甲方或内部拿事实资料

这类问题不是让甲方设计产品，而是让他们提供客观事实。

示例：

- 当前有哪些 API。
- 订单、支付、设备、机器人会返回哪些状态。
- 当前试点点位在哪里、有什么设备。
- 实际出现过哪些异常案例。
- 支付和退款的账户主体是谁。
- 两个月窗口期的真实截止时间和工程资源。

处理方式：

- 直接索要资料、字段、样例、截图、日志和数据。
- 不让甲方用抽象语言描述“想要什么系统”，而是让他们提供事实证据。

## 4. 原问题的重新处理

### 4.1 产品边界

原问题（不再直接询问）：

1. RoboOps 第一版是只服务饮品场景，还是从一开始就要支持多场景模板？
2. 第一版是否必须支持多客户/多租户？
3. 己方是否作为平台运营方参与日常运营，还是只把系统交给客户方使用？
4. 小程序是否属于 RoboOps 的产品范围，还是只需要与小程序打通？
5. 机器人本体的管理边界到哪里？

更新判断：

- 第 1 个问题我们已经可以回答：从一开始按多场景模板设计，饮品只是样板。
- 第 2 个问题建议按多租户/多客户模型预留，但 MVP 可以先开放单租户或少量租户。
- 第 3 个问题不能只问客户，应同时支持客户自营、平台代运营、联合运营三种模式。
- 第 4 个问题建议 RoboOps 先作为运营中枢，与小程序打通；是否包含消费者端 UI 可后置。
- 第 5 个问题建议区分机器人本体控制和商业运营管理，MVP 先做状态、事件、日志、任务和有限命令记录。

仍需确认的事实：

- 当前小程序、订单系统、支付系统是否已经存在。
- 现有机器人/设备 API 能上报哪些事件。
- 第一版是否必须给客户独立登录使用，还是先内部/代运营使用。

### 4.2 用户与权限

原问题（不再直接询问）：

1. 客户方有哪些真实使用角色？
2. 谁能退款？
3. 谁能修改商品和流程？
4. 谁能处理异常？
5. 谁只能查看数据？
6. 点位运维人员是否需要移动端？

更新判断：

- 不应直接问客户“你们有哪些角色”，因为他们可能没有团队。
- 我们应该提供默认角色模板：业务负责人、租户管理员、运营负责人、点位负责人、客服/售后、设备运维、现场维护、财务、审计、平台支持。
- 谁能退款、谁能修改配置、谁能处理异常，应由角色模板和权限包决定。
- 点位/现场角色大概率需要移动端友好的任务视图，但 MVP 可以先用响应式页面或轻量任务页承接。

仍需确认的事实：

- 客户第一批实际能指定哪些人承担业务负责人、运营、设备、现场、财务职责。
- 是否由平台方先代运营。
- 是否有外部供应商或点位方需要登录。

### 4.3 订单流程

原问题（不再直接询问）：

1. 当前完整订单状态有哪些？
2. 支付成功后，订单如何进入设备/机器人执行队列？
3. 制作失败时订单如何处理？
4. 顾客未取货如何判断？
5. 顾客未取货后，订单是否可退款、重做或丢弃？
6. 订单状态由哪些系统产生，哪些状态可以人工修改？

更新判断：

- 订单生命周期应由 RoboOps 主动定义标准状态，再映射现有 API 状态。
- 标准底层状态可使用：已创建、待支付、已支付、待执行、已分配、执行中、执行完成、待交付、已交付、未交付、异常、已取消、退款中、已退款。
- 人工可修改的状态必须严格受权限控制并留痕。
- 顾客未取货不应只靠一个字段判断，应结合设备事件、机器人感知、超时规则和人工确认。

仍需确认的事实：

- 现有订单 API 和支付回调字段。
- 设备/机器人执行队列的接口方式。
- 当前是否已有取货检测、柜门、扫码、视觉或机器人判断事件。
- 是否有真实订单卡住、未取货、制作失败的案例日志。

### 4.4 异常处理

原问题（不再直接询问）：

1. 当前最常见的异常有哪些？
2. 哪些异常可以自动恢复？
3. 哪些异常必须现场处理？
4. 哪些异常需要客服介入？
5. 哪些异常需要工程师排查？
6. 异常是否需要分级？
7. 异常是否需要超时提醒？

更新判断：

- 异常分类应由 RoboOps 先设计，不应等客户整理。
- MVP 至少应覆盖：支付异常、订单下发失败、机器人接单失败、执行失败、执行超时、顾客未取走、取货判断不确定、设备离线、物料/资源不足、点位环境问题、退款争议、配置错误。
- 异常必须分级，至少支持 P0/P1/P2/P3 或高/中/低。
- 异常必须有默认负责人、处理状态、SOP、通知和超时升级。

仍需确认的事实：

- 已经发生过的 5-10 个真实异常案例。
- 设备错误码和机器人错误码。
- 哪些异常当前工程上可以自动恢复。
- 哪些异常必须依赖现场人员。

### 4.5 商品/服务流程

原问题（不再直接询问）：

1. 咖啡和奶茶的流程差异具体是什么？
2. 哪些流程是所有场景通用的？
3. 哪些流程必须按客户定制？
4. 商品规格、配方、制作步骤是否需要后台配置？
5. 第一版需要配置到什么粒度？

更新判断：

- 不能把“咖啡/奶茶差异”当作产品边界。
- 应抽象为商品/服务类型、属性、SKU/规格、履约模板、资源消耗、异常规则。
- 通用流程是：可售对象配置、下单、支付、分配执行、执行过程、交付/取货、异常、售后、报表。
- MVP 先支持商品/服务目录、规格/选项、上下架、适用点位、绑定履约模板。
- 配方引擎和复杂制作步骤可以后置，但字段要预留。

仍需确认的事实：

- 当前饮品设备或机器人实际需要哪些商品字段。
- 现有小程序商品模型。
- 设备端是否需要接收配方、制作参数或只是接收商品编码。

### 4.6 财务与结算

原问题（不再直接询问）：

1. 当前支付通道是谁管理？
2. 收入进入谁的账户？
3. 退款由谁发起和审批？
4. 是否需要对账导出？
5. 是否需要按客户/点位/商品维度统计收入？

更新判断：

- 收入、退款、对账是运营后台必须保留的能力，即使 MVP 不做完整财务系统。
- 退款发起和退款审批应分离，至少在权限模型中预留。
- 按客户、品牌、点位、商品/服务维度统计收入是后续必然需求。
- MVP 先做交易、退款、收入统计和导出占位。

仍需确认的事实：

- 当前支付主体、收款账户和退款接口归属。
- 是否涉及平台代收、客户自收、点位方分账。
- 是否有财务对账格式或结算周期要求。

### 4.7 实施节奏

原问题（不再直接询问）：

1. 两个月窗口期的具体截止日期是什么？
2. 第一批必须上线的客户是哪一家？
3. 第一批必须支持多少个点位？
4. 是否已有前端/后端工程资源排期？
5. 第一版上线成功的验收标准是什么？

更新判断：

- 这些问题仍然需要确认，因为它们是项目管理事实，不是让甲方定义产品。
- 但验收标准我们可以先给建议：能建品牌、建点位、绑定设备、配置商品/服务、接入或模拟订单、查看生命周期、生成和处理异常、分配角色、查看基础报表。

仍需确认的事实：

- 真实截止日期。
- 试点客户/点位优先级。
- 可用工程资源。
- 是否需要展会或样板间 Demo。

## 5. 不建议再直接问甲方的问题

以下问题容易让没有经验的甲方卡住，建议改成“我们给方案，请他们确认”。

| 不建议直接问 | 更好的方式 |
| --- | --- |
| 你们有哪些运营角色？ | 我们提供最小运营团队模板，让他们指定谁承担哪些职责 |
| 你们订单流程是什么？ | 我们提供标准订单生命周期，再映射他们已有接口状态 |
| 你们异常怎么处理？ | 我们提供异常分类和默认分派规则，让他们补充真实案例 |
| 哪些权限给谁？ | 我们提供角色权限矩阵，让他们选择自营/代运营/联合运营模式 |
| 咖啡和奶茶流程差异是什么？ | 我们抽象商品/服务履约模板，再用饮品场景校验 |
| 第一版要做哪些后台功能？ | 我们给 MVP 范围，让他们按上线目标删减或确认 |
| 哪些东西需要定制？ | 我们先用配置模型承载差异，只把不能配置的部分列为定制风险 |

## 6. 仍需拿到的事实资料

这些资料仍然重要，但它们是“事实输入”，不是“产品定义权”。

### 6.1 接口与系统资料

- 现有 API 文档。
- 现有物联网设备管理后台截图或演示账号。
- 小程序下单链路说明。
- 支付状态回调说明。
- 设备/机器人状态字段说明。
- 订单状态字段说明。
- 异常码/错误码列表。
- 日志或事件上报格式。
- 当前是否已有订单系统、商品系统、支付系统、设备系统。

### 6.2 真实业务资料

- 深圳现有试点点位列表。
- 每个点位的设备配置。
- 每个点位的营业模式。
- 每个点位目前真实订单量。
- 点位异常案例。
- 现场人员目前如何处理问题。
- 客户现在最痛的 5 个真实运营场景。

### 6.3 约束资料

- 两个月窗口期的具体截止时间。
- 第一批必须支持的点位和客户。
- 工程资源排期。
- 哪些系统已经确定不能改。
- 哪些品牌项目资料可脱敏参考。
- 哪些客户资产或流程不能复用，避免版权/IP 风险。

### 6.4 商务与责任资料

- 收款主体。
- 退款主体。
- 客服责任归属。
- 现场维护责任归属。
- 设备故障责任归属。
- 是否需要平台代运营。
- 是否有外部供应商或点位方参与。

## 7. 我们应主动产出的答案

以下内容不应等待客户输入，应由 RoboOps 产品规划主动给出。

### 7.1 标准产品方案

- 产品定位。
- MVP 范围。
- 信息架构。
- 页面清单。
- 核心数据模型。
- 状态模型。
- 异常模型。
- 配置模型。

### 7.2 运营方法方案

- 按规模阶段的团队搭建建议。
- 自营、代运营、联合运营、加盟/区域代理的组织模型。
- 角色模板。
- 权限矩阵。
- 异常分派规则。
- 运营 SOP。
- 上线检查清单。

### 7.3 场景模板方案

- 饮品亭模板。
- 通用机器人服务站模板。
- 后续可扩展的零售、讲解、配送、清洁、实验室工作站等模板。
- 每个模板对应的商品/服务属性、履约状态、异常字典和推荐角色。

### 7.4 Demo 与样板方案

- 一个可演示的品牌。
- 一组样板点位。
- 一组机器人/设备。
- 一组商品/服务。
- 一组正常订单和异常订单。

## 9. 对后续文档的影响

后续 PRD 和页面设计不应再以“待甲方确认”为主要前提，而应采用以下口径：

- 先定义 RoboOps 推荐的标准运营模式。
- 再通过配置支持不同甲方差异。
- 再通过试点数据验证和修正。
- 最后才把无法配置的部分列入定制或后续版本。

这意味着下一步文档应重点产出：

1. `06-PRD-v0.1.md`：基于当前判断直接形成第一版产品需求。
2. `07-信息架构与页面清单.md`：把运营对象转成后台页面。
3. `08-核心数据模型ERD.md`：明确可配置对象和关系。
4. `09-MVP原型与演示数据方案.md`：给没有经验的甲方一个可理解、可选择、可演示的样板。
