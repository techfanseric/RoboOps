# RoboOps MVP 真实运营闭环审查与补强记录

整理日期：2026-07-05
检查对象：`/Users/ericyim/RoboOps/app`

## 1. 审查结论

上一版静态 MVP 已有完整模块轮廓，但经营逻辑仍偏展示型。核心缺口是运营事实没有贯穿：

- 工作台、点位、订单、异常、任务、退款、报表之间有并列展示，但缺少共享状态。
- 异常动作能生成记录，但没有稳定影响订单状态、任务状态、退款状态和报表。
- 点位上线检查只是清单，没有成为点位是否可营业的准入条件。
- 报表存在字段，但没有从当前请求、异常、任务、设备事件和退款记录中推导。
- 团队搭建、权限包和审批策略已经出现，但还没有真正控制动作。

本次补强后的 MVP 已经从“页面骨架”推进为“可运营骨架”：静态阶段先验证经营事实，React/Vite 阶段再把这些事实沉淀进类型、服务层、共享状态和路由。

## 2. 真实 MVP 的判定标准

RoboOps 的 MVP 不能只是功能最小。它必须满足以下条件：

| 标准 | 含义 | 当前状态 |
| --- | --- | --- |
| 可上线 | 点位能判断是否具备开业条件 | 已补上线准入状态和阻塞项 |
| 可接单 | 请求能进入履约状态并关联设备事件 | 已补请求详情和执行事件 |
| 可处理异常 | 异常能分派、推进、转任务、转退款、关闭 | 已补动作联动 |
| 可追责 | 关键动作有处理记录和审计日志 | 已补处理记录和操作日志 |
| 可复盘 | 工作台和报表从经营事实推导 | 已补动态指标和异常原因统计 |
| 可配置 | 场景模板、权限包、审批策略、团队建议能表达差异 | 基础具备，工程化阶段需持久化 |

## 3. 本次识别的 P0 逻辑缺口

### 3.1 工作台缺口

原状态：

- KPI 主要依赖静态字段。
- 点位健康使用手填的订单数和异常数。
- 没有表达上线、履约、异常、任务、退款、复盘之间的经营链路。

补强：

- 工作台新增“经营闭环”状态：上线准备、接单履约、交付完成、异常处理、任务执行、退款售后、运营留痕。
- KPI 改为从当前筛选范围内的点位、设备、请求、异常、任务、退款记录推导。
- 点位健康分数改为由在线设备、待处理异常、待处理任务、上线阻塞项综合计算。

### 3.2 点位上线缺口

原状态：

- 点位有营业状态，但缺少“是否真的能开业”的准入判断。
- 上线检查与点位状态没有关系。

补强：

- 新增点位“上线准入”状态：可营业 / 待处理。
- 点位详情展示阻塞项，例如设备维护、营业确认、可售商品/服务、设备在线。
- 点位列表加入上线准入、动态在线设备、动态请求数、待处理异常数。
- 点位负责人、营业状态和上线检查项已经进入配置发布流程；审批通过后才会改变点位当前经营状态并写入审计。

### 3.3 订单/请求缺口

原状态：

- 请求详情能看执行事件，但异常动作不会反向改变请求状态。
- 退款记录只展示，不会改变请求支付/履约状态。

补强：

- 异常转退款时，请求状态同步为“退款处理中”。
- 异常关闭或任务解决后，请求状态同步回到待交付/待确认。
- 异常推进、任务完成、退款创建会追加执行事件。

### 3.4 异常处理缺口

原状态：

- 异常可推进、关闭、转任务、转退款，但这些动作仍比较孤立。

补强：

- 转任务会把异常状态改为“已转现场处理”。
- 转退款会把异常状态改为“已转退款”，并创建退款记录、更新请求状态、写入执行事件。
- 关闭异常会根据退款记录或异常类型更新关联请求状态。
- 所有动作写入处理记录和审计日志。

### 3.5 任务工单缺口

原状态：

- 任务列表和详情存在，但任务不能推进。
- 异常转任务后，任务完成不能反向影响异常。

补强：

- 任务新增“开始处理”和“标记解决”动作。
- 任务解决后，来源异常更新为“已恢复”。
- 若任务关联请求，请求状态同步到待交付/待确认，并写入执行事件。

### 3.6 报表缺口

原状态：

- 异常原因是硬编码比例。
- 日报指标是说明性字段。

补强：

- 异常原因根据当前筛选范围的异常类型动态统计。
- 日报指标显示当前请求总量、完成数、异常/退款中数量、可营业点位、在线设备、收入和退款处理中数量。
- 退款/售后记录作为独立复盘区块展示。

## 4. React/Vite 阶段完成情况

正式工程首轮升级已经补齐：

- `local service`：异常、任务、筛选、团队建议等动作通过 `app/src/services/operations.ts` 统一处理。
- `TypeScript model`：请求、异常、任务、退款、日志、点位准入、权限、角色等已建立明确类型。
- `routing`：全部一级模块已通过 React Router 接入。
- `derived reports`：工作台与报表从当前请求、异常、任务、退款、设备状态和点位准入推导。
- `detail actions`：异常详情和任务详情已接入与列表一致的处理动作。
- `release approval`：配置发布可新建、生成审批单、审批通过或驳回，并更新发布状态。
- `catalog configuration`：商品/服务目录可申请配置变更，审批通过后更新 SKU 可售范围，并影响后续点位可售判断。
- `point configuration`：点位配置可申请变更，审批通过后更新营业状态、负责人和上线检查项，并影响点位准入、健康分和详情直链。
- `template configuration`：场景模板可申请配置变更，审批通过后更新业务对象、字段、履约状态、异常类型和责任角色。
- `brand and organization configuration`：品牌资料与组织/区域可申请配置变更，审批通过后更新当前品牌或组织，并写入发布、审批和审计记录。
- `device configuration`：设备名称、归属点位、类型、运行状态、版本和能力标签可申请配置变更，审批通过后更新设备台账、追加设备事件并写入审计。
- `device command control`：设备命令可按风险执行；低风险命令直接写入命令记录、设备事件和审计，高风险命令审批通过后才执行。
- `role activation`：团队搭建生成的角色实例可绑定账号、数据范围和权限包，提交权限审批，审批通过后参与当前账号有效角色判断并写入 L4 审计。
- `invitation acceptance`：用户邀请支持独立接受页；受邀人未登录时可设置密码创建账号，已登录会话需要先退出，已接受或过期邀请会被拦截；新账号默认只有“待授权用户”基础角色，只能看到授权等待页，不展示经营数据，必须再经过角色实例绑定和审批才获得业务权限。
- `api operation outbox`：关键经营动作会生成服务端同步记录，包含方法、路径、风险、对象、业务状态、幂等键、同步状态、重试次数、错误原因、服务端请求号和补偿处理，为真实 API 接入提供边界。
- `state persistence`：浏览器会保存当前操作状态，便于连续验证。
- `permission guard`：当前账号的数据范围已影响顶部筛选、列表、详情直链、动作按钮、审批队列、操作日志和报表日志。
- `menu permission guard`：当前账号有效角色和权限包会控制一级菜单显示与路由访问，越权 URL 会进入无菜单权限说明页，角色页展示当前账号菜单授权来源。
- `role login views`：已补齐平台支持、租户管理员、业务负责人、运营负责人、点位负责人、配置、客服、退款、设备、现场、财务、数据、审计、试运行等账号视角；正式界面只显示当前登录账号，角色页提供账号与职责矩阵用于验收。
- `dynamic navigation`：侧边栏数量已从当前可见经营事实派生，不再使用静态演示数字。

仍需进入下一阶段：

- `permissions`：当前为前端样例策略，菜单权限、路由守卫、动作权限和数据范围已有基础接入；后续需要接真实登录、服务端授权、服务端权限矩阵、结构化数据范围和后端二次校验。
- `role approval`：当前角色实例启用、复核和回收均已进入前端审批流；复核/回收申请提交后不会提前改变权限，审批通过后才延长有效期或回收权限。后续需要接服务端 IAM、多级审批、到期自动冻结和定期复核任务。
- `approval policy`：当前已有单级审批、自审拦截、角色和范围判断，后续需要补金额阈值、影响范围阈值、多级审批和超时升级。
- `device command`：当前已有前端命令审批和执行记录，后续需要接真实设备通道、执行回调、失败/超时和重试策略。
- `configuration editors`：商品/服务、点位、场景模板、品牌、组织和设备已具备基础变更发布联动；通用配置发布、对象级发布和角色实例授权已写入结构化范围；对象级配置发布已具备受控回退申请和反向应用；租户/客户开通已能生成初始租户、品牌、组织和管理员邀请，用户邀请、接受、账号创建和角色实例审批链路已在前端跑通；后续仍需补字段级校验、邮件/短信投递、服务端 IAM、服务端版本锁、冲突处理和真实服务端持久化。
- `server audit`：当前为前端样例留痕，后续需要服务端不可篡改日志、前后值、操作者来源和真实审批记录。
- `API adapter`：当前已有服务端同步记录、路径映射、同步中、成功、失败、需补偿和已补偿状态；后续需要接真实 HTTP client、自动重试、服务端分页、真实数据同步和对象级补偿执行。

## 5. 下一阶段准入标准

进入真实 API 与权限阶段前，建议把“能不能进入下一阶段”的判断改成以下标准：

1. 新客户初始化后，系统能生成组织、角色、权限包、异常分派、审批策略和上线检查。
2. 点位只有在负责人、设备、商品/服务、异常规则和配置发布满足条件后才显示为可营业。
3. 一笔请求必须能看到支付/确认、执行事件、设备、异常、任务、退款和处理记录。
4. 异常处理必须能改变相关请求、任务、退款、日志和报表。
5. 任务完成必须能回写异常和请求状态。
6. 报表只展示由请求、事件、异常、任务、退款、设备状态推导出的数据。
7. 高风险动作必须有权限、审批或二次确认记录。

## 6. 当前结论

当前 React/Vite MVP 可以继续作为真实 API 和权限接入的工程底稿，但不能再按“页面覆盖率”评价质量。之后每新增一个模块，都要回答三个问题：

- 它改变了哪个经营事实？
- 它影响哪些下游对象？
- 谁负责、谁审批、谁能复盘？

只有这三件事成立，RoboOps 才具备可运营的商业运营平台价值。
