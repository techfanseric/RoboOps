## Business Context

原业务更接近设备能力和 IoT 后台，主要关注设备状态、基础订单量和接口能力。新客户类型是人形机器人公司，这类客户希望把咖啡、奶茶或服务亭业务变成由人形机器人参与履约的商业场景，但自身缺少成熟的门店运营、订单异常、客服、退款、点位管理和人员分工经验。

因此，只提供 API 不足以让客户把业务跑起来。RoboOps 应作为机器人商业运营平台，帮助客户从点位、设备、商品/服务、订单/请求、异常、任务、人员权限、报表和配置发布上形成完整运营闭环。

## Key Judgments

- RoboOps 是可配置的机器人商业运营平台。
- MVP 不能写死茶、咖啡或单一饮品场景，饮品亭只是一个样板场景。
- 系统要把 API 状态转成业务状态、责任人、SLA、处理动作和审计记录。
- 客户大概率没有完整商业运营团队，因此系统应提供默认组织角色和团队搭建建议。
- 人形机器人会带来传统设备运营没有的判断、交互、执行和取货异常。
- 首期目标是能跑起来、能卖单、能处理基本异常，不追求一步到位。

## Product Requirements Mentioned

- 点位、机器人、设备、商品/服务、订单/服务请求需要统一管理。
- 订单支付、制作/执行、取货/交付、退款、异常和任务要有状态闭环。
- 异常要能分派到运营、客服、设备运维、现场维护、配置人员等角色。
- 角色、权限包、数据范围和审批策略需要可配置。
- 客户组织缺少团队时，系统要给出可采纳的角色模板和团队搭建方案。
- 不同场景的业务对象、字段、状态、异常字典和责任角色应可配置。
- 系统要支持后续复制到多客户、多品牌、多点位，并沉淀为标准产品。
